# Actions

## What it is

Board actions change something outside the board. The first one merges a PR that is waiting on you (a handed-back wave PR, a reviewed fix PR, or the final plan PR) with `gh pr merge`. The second appends your answer to a queue entry waiting on you. The third resumes a run's session with `continue` or `go` (see [resume.md](resume.md)). Every merge, answer, and resume request goes in the action log. The server side is `packages/server/src/action-routes.ts`, `gh-actions.ts`, `answer-routes.ts`, `queue-writer.ts`, and `action-log.ts`. The routes sit behind the action guard (see [server.md](server.md)). The page's confirm step is U1's (screen 1).

## How it works

- **Routes.** `POST /api/actions/merge-preview` `{ repoId, number }` and `POST /api/actions/merge` `{ repoId, number, headSha }`. The repo comes from the current Board by `repoId`. A path in the body is ignored. The PR must be in the model's `waitingPrs(repo, now)`.
- **Checks, in order.** Merge: `number` must be a positive integer and `headSha` 40 lowercase hex, else `400 bad request`. Preview: a string `repoId` and a positive integer `number`, else `400`. Then, for both routes: repo not on the Board or PR not waiting → `404 not waiting on you`. Then gh status not `ok` → `503 gh unavailable`. `unknown` (before the first `gh auth status`) counts as not ok. Then, for merge only: a merge already running for the same repo and PR → `409 merge in progress`. The slot is taken before the first gh read and freed when the request ends, failure included. No gh command runs before these checks pass.
- **The read.** `gh pr view <n> --json number,state,url,title,headRefOid,mergeable,mergeStateStatus,statusCheckRollup,autoMergeRequest`. The preview maps `headRefOid` → `headSha`, `mergeable` (`MERGEABLE`, `CONFLICTING`, anything else → `unknown`), `mergeStateStatus` → `mergeState`, and the checks rollup (the same rule as the Board's `checks`). It is not usable when gh fails, the JSON is bad, the state is unknown, `headRefOid` isn't a 40-char sha, or `url` isn't exactly `https://github.com/<owner>/<name>/pull/<number>` for this number. The preview answers `502` with gh's stderr, or `gh failed`.
- **The merge.** First a fresh read. If it fails, the result is `failed` with its text, and no merge runs. If its head isn't `headSha`, the result is `stale` with the current `headSha`, and no merge runs. Otherwise the server runs exactly `gh pr merge <url> --merge --match-head-commit <headSha>`. The `<url>` comes from that fresh read. The call has a 60 s timeout, and it never passes `--admin`, `--auto`, `--squash`, `--rebase`, or `--delete-branch`. Then the server always reads the PR again:
  - `MERGED` → `merged`.
  - Open with `autoMergeRequest` set → `auto-merge`.
  - Open, no auto-merge, and the call succeeded → the server asks GitHub whether the PR is in a merge queue: `gh api graphql` with `repository(owner:, name:) { pullRequest(number:) { mergeQueueEntry { state } } }`, owner and name from the re-read's url, default timeout. An entry → `queued`. No entry, or the query fails → `unconfirmed`, `gh ran the merge, but GitHub hasn't confirmed the merge yet. Check it on GitHub.` This is the only case that asks; see **Why**.
  - Else, if the call failed (timeout included) → `failed` with gh's stderr: escape codes removed, trimmed, and at most 500 chars. An empty stderr reads `gh pr merge failed`.
  - `CLOSED` → `failed`, `PR is closed`.
  - The re-read failed after a successful call → `unconfirmed`, with a message to check GitHub.
  - So `unconfirmed` means the call succeeded but GitHub hasn't shown the result: either the re-read failed, or the PR is still open and not in a merge queue.
- **Answer route.** `POST /api/actions/answer` `{ repoId, line, text }` (`answer-routes.ts`, mounted beside the merge routes under the one `actions` Hono). Checks, in order, with nothing written, logged, or rebuilt before the write: a field missing or not a string → `400 bad request`. `cleanAnswer(text)` fails → `400` with its error (see [run-model.md](run-model.md)). `repoId` not on the current Board, or no item on that repo's `model.queue` whose `line` equals `line` and is `isAnswerable` → `404 not waiting on you` (any Board repo, registered or claim-only). An answer already writing for that repo → `409 answer in progress` (the slot is per repo, freed when the request ends, failure included). Then `200 { outcome, message?, logged }`.
- **The queue write** (`writeAnswer` in `queue-writer.ts`; its file calls are an injectable `QueueFs`, Node by default). The file is `path.join(repo.path, 'pod-docs/handoff-queue.md')`. Its realpath must sit under the repo's realpath, else `failed`, `queue file is outside the repo`, and nothing is read or written. A queue linked to another file inside the repo is written at that real file. A missing file (or repo) → `changed`, `The queue file is missing.`, and it is never created. The file is read as bytes. Exactly one line whose trim equals `line` → write. None → `changed`, `The entry changed since you looked.` Several → `changed`, `Two entries read the same. Answer it in the chat.` Only that line's bytes change: its indent (and a BOM on the first line), its trailing spaces and `\r`, the other lines' endings, bytes that aren't UTF-8, and whether the file ends with a newline all stay. The new file goes to `.<name>.<random>.tmp` beside the real file (the watcher counts only `.md`). Then the queue is read again. If it changed since the first read → `changed`, `The queue changed while saving. Look again.`, temp removed. Else the temp is renamed over it, retried 3 times 100 ms apart on `EPERM` or `EBUSY`. Still failing, or any other error → `failed`, `Couldn't write the queue (<code>).`, temp removed, queue untouched.
- **After the merge call.** Once the merge call has run, the server drops the PR's gh cache entries (`GhCache.forget`: the entry by number, and any branch entry holding that number) and asks gh again. This happens before the response.
- **Action log.** One `ActionEntry` per merge request that passed the checks above: `stale` and `failed` too, but not `400`, `404`, `503`, `409`, or previews. `target` is `PR #N`, `repo` is the repo's name, and a stale entry's message is `head now <sha7>`. One entry per answer request that reached the write (`answered`, `changed`, `failed`), with `action: 'answer'`, the write's message, and `target` `<date> · <TYPE> · <from → to>` from the entry's header, never the answer text or the body. One entry per resume the runner was asked to start, by the route (`auto: false`) or the automatic check (`auto: true`): `action: 'resume'`, `result` `started` or `failed`, `reply` `continue` or `go`, the runner's message, and `target` `<run> · <word>`. Turning a toggle on or off isn't logged. The reader keeps a line only when its `result` belongs to its `action` (merge: `merged`, `queued`, `auto-merge`, `stale`, `failed`, `unconfirmed`; answer: `answered`, `changed`, `failed`; resume: `started`, `failed`, with a `reply` of `continue` or `go` and a boolean `auto`), so old merge and answer lines still read. On screen 1, `started` gets the ok chip and `failed` bad, and an automatic entry reads `auto`. On screen 1, `answered` gets the ok chip, `changed` you, and `failed` bad. `NewActionEntry` is the entry before the log stamps `at`: `Omit` spread over the union, so `action` and `result` stay paired. Each entry is one JSON line appended to `<config dir>/actions.jsonl` (the folder of `config.json`), owner-only on POSIX. The file appears with the first merge. At start the server reads the newest 50 good lines. It skips bad lines, and a missing or unreadable file gives an empty list. If the last line was cut short, the next entry starts on a new line. If the append fails, the response is the same except `logged: false`, and the entry isn't listed.
- **The Board.** `Board.actions` is the log's newest 50, newest first, read on every build. After every logged merge, answer, or resume request, the server rebuilds the Board and sends it before the response, so it shows the new entry and the PR's fresh state.

## Why it's this way

- **`queued` only from a merge-queue entry.** gh 2.92's `pr view --json` has no merge-queue field, so the server asks GraphQL's `mergeQueueEntry`. An open PR after a successful call can also be GitHub's re-read lagging a plain merge on a repo with no queue. Calling that `queued` would say "Added to the merge queue", which is false. The board shows only what GitHub reports, so anything GitHub hasn't confirmed is `unconfirmed`. The Board's next gh read then shows `merged`.
- **The queue is asked only in that one case.** A merged, closed, or auto-merge re-read already says what happened, and a failed call has gh's own text. Asking only there keeps the extra gh call off every other path.
- **`merged` only from the re-read.** gh's exit code doesn't say what happened. A timeout can still merge, and a success can mean queued. The re-read is the only proof.
- **`--match-head-commit`.** It refuses the merge if anything was pushed after you looked. That includes autopilot racing you on a wave PR.
- **The answer goes at the end of the line.** See [run-model.md](run-model.md): one line per entry, and the end keeps `parseQueue`'s reading. An answer clears nothing: pod still waits until it reads the line.
- **Bytes, not text.** The writer splices one line's bytes, so a CRLF file, a BOM, or a stray non-UTF-8 byte elsewhere is never rewritten.
- **A write by pod wins.** pod may append to the queue while you answer. The re-read before the rename turns that into `changed` instead of losing pod's line.
- **Retry on `EPERM` and `EBUSY` only.** On Windows an editor or a scanner can hold the file for a moment; other codes won't pass on a retry.
- **No merge on a failed fresh read.** Without a read, the server can't check the head or the url, so it doesn't merge.
- **The url from the fresh read, checked.** The url passed to `gh pr merge` must be a GitHub pull url for that number, so a different host or PR is never passed.

## Watch out

- The real gh field names were taken from `gh pr view --json` (no fields), gh 2.92.0. `mergeQueueEntry` was checked with a read-only `gh api graphql` query on `iamphduc/pod-board` #27 (`null`). A gh that adds a merge-queue field to `pr view --json` could replace the extra call.
- In the GraphQL call, owner and name go with `-f` (raw string). `gh api -F` converts values: a repo named `123` would become a number, and `@…` would read a file. Only `number` uses `-F`.
- Tests and smoke runs never merge a real PR: tests use a fake gh exec, and the smoke recipe only checks the `404` and `403` previews.
- `actions.jsonl` is in the config folder, which the watcher watches. The config folder's filter keeps only `config.json`, so an append doesn't trigger a rebuild. The route rebuilds the Board itself.
- The answer write is the board's first write into a repo. It only appends to one line of a git-tracked file; `git checkout pod-docs/handoff-queue.md` undoes it. Tests and smoke runs write only to temp copies.
- The rename gives the queue the temp file's mode (the default for new files), so an unusual mode on the queue file isn't kept.
- The whole log file is read once at start. It is never trimmed, so it grows by one line per merge.
