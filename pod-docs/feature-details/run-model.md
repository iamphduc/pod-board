# Run model

`buildRepoModel(files)` in `packages/model/src/run-model.ts` turns one repo's pod docs into plans → sprints → waves → slices, plus the handoff queue. The server reads the files; the model only gets their text as a `RepoFiles` map (repo-relative path → text). It never throws: a missing, empty, or odd file gives `unknown`, empty, or absent fields.

`parseAgentTranscript` in `packages/model/src/transcript.ts` turns one pod agent's transcript into an `AgentRun`, and `agentState` says whether the agent is still running. The board types the server sends (`Board`, `BoardRepo`, `AgentRun`, `PrStatus`, `Claim`) are in `packages/model/src/board.ts`.

It builds on the ported pod-flow parsers (`packages/model/src/pod-flow/`, kept as a faithful copy) and the format readers (`packages/model/src/formats.ts`). Changes go in `run-model.ts` or new modules, never in the copy.

## Rules

- **Docs gate.** `docs` comes from the `pod docs: <N>` line of `pod-docs/README.md`. Any version other than 2, or no README, returns `plans: []` and `queue: []` with nothing else read. Why: an older or newer layout would parse into a wrong board, and a wrong board is worse than an empty one. The older `docs/` layout has no `pod-docs/README.md`, so it reads as unsupported.
- **Keys.** `\` in keys becomes `/` first, so a Windows snapshot gives the same model.
- **Plans.** Each `.md` directly in `pod-docs/plans/` or `pod-docs/plans/archive/`; slug from the file name; sorted by slug. Other files (`.gitkeep`, `.txt`) and deeper folders are ignored. The same slug in both folders → the archived copy. Title and status come from `parsePlan`; `portBase` and `go` from `planExtras` (`go` is always `'unknown'`: pod doesn't record it yet). A sprint-table row with an empty Sprint cell is skipped.
- **Sprint docs.** Each `.md` directly in `pod-docs/sprints/` (`isArchived: false`) and `pod-docs/sprints/archive/` (`isArchived: true`), keyed by the `Slug:` header, else the file name. The same slug in both → the archived copy, since archiving is the last step of a sprint.
- **Joining.** A doc joins the plan its `From plan:` names. With no `From plan:`, it joins the first plan (by slug) whose sprint table lists it. A doc whose `From plan:` names a plan that isn't there, or that no table lists, is dropped: the board can't place it.
- **Sprint order.** The plan's sprint-table order, then docs that name the plan but aren't in its table (by slug).
- **Sprint status.** Row `done` or archived doc → `done`; row `active` or a live doc → `active`; row `planned` → `planned`; anything else → `unknown`. A live doc wins over a `planned` row, because pod writes the doc when the sprint starts and may not have updated the plan yet. A row with no doc has `hasDoc: false` and `waves: []`.
- **Waves and slices.** Board rows grouped by wave number, waves ascending, slices in table order. A wave cell that isn't a number reads as wave 0 (the parser's rule). `pr` is `prRef(cell, status)`. `dependsOn` is `sliceDeps` of the board's `Depends on` cell (`parseSprint` drops that column, so it's read again from the same table, row for row); no such column → `[]`. Values are kept as written, even when they match no code on this board: older boards name slices by word (`geometry`), and a dependency may sit in an earlier sprint.
- **Current.** `currentSprint` is the first sprint, in sprint order, that isn't `done`; absent when all are done or the plan is `archived`. `currentWave` is the lowest wave with a slice that isn't `isDone` (a `blocked` or `skipped` status counts as not done, even with a merged PR cell); absent with no doc, no slices, every slice done, or a sprint whose status is `done`. Why: a sprint that finished with a blocked or skipped slice is over, and pointing at that wave would show it as still running.
- **Per-slice detail.** Each slice reads its `### <code>: <title>` section of the sprint doc (the code before the colon must match exactly; the first such section wins). The section runs to the next `##` or `###` heading. Only top-level bullets count as fields, so a `**Model:**` inside the Scope text isn't the field. `model` is the first word of `- **Model:**`, lowercased (`sonnet 4.5` → `sonnet`). `filesOwned` is every backticked path in `- **Files owned:**` and the deeper lines under it, in order; with no backticks, the text split on commas. Notes in brackets after an item drop out first: a `(` at the start or after a space, outside backticks, to its matching `)`, so `(new)` and `(new, incl. view.ts, …)` (names in backticks or not) name no file. Why: the names in such a note are shorthand for files under the glob before it, not repo paths. A bracket inside a path (`app/(group)/page.tsx`) stays, and an unclosed one leaves the text as written; a lone dash names no file. Paths are kept as written, even shorthand such as `SetupCard.css` that real docs write after a full path. `oneWayDoor` is the text of `- **One-way door:**`, absent when it's empty or starts with the word `none`. No section → no `model` or `oneWayDoor`, and `filesOwned: []`.
- **Queue.** The repo's `queue` is every entry of `pod-docs/handoff-queue.md` in file order, each with `needsYou`. A plan's `queue` holds entries whose `plan:` is its slug, or, with no `plan:`, whose `sprint:` is one of its sprints. An entry naming neither joins a plan only when it's the orchestrator's hand-back of that plan: from `orchestrator`, its body starting `plan <slug> complete` (the slug may be in backticks; any case for `plan` and `complete`). Other entries naming neither stay only on the repo. Why: pod's plan-complete step writes the hand-back as `plan <slug> complete — final PR <url> …`, and real ones (chess-web `ui-polish`) carry no `plan:` tag, so the run never reached `final PR`. A missing queue file → `[]`.
- **Queue items** (`queue-answer.ts`, re-exported from `run-model.ts`). Each item also has `line`, its whole line trimmed, which is its identity for the answer write; `date`, the header's first part, absent when that part is blank; and `answer`. `queueLines(md)` uses `parseQueue`'s split, trim, and line regex, so its list matches the entries one for one. `splitAnswer(rest)`: only a `**Answer (human):**` marker (any case) after the entry's first `**Resolution:**` counts; the answer is the text after it, up to a later `**Resolution:**`, trimmed. A marker quoted in the body, before the Resolution, is body text (plan fix pass, PR #34). The body is `parseQueue`'s, also cut at the answer marker, so it never holds the answer. An empty `**Answer (human):**` still counts as answered, so an entry isn't answered twice. The ported `parseQueue` is unchanged.
- **Answer format.** The board appends ` **Answer (human):** <text>` at the end of the entry's line (`withAnswer`), after its `**Resolution:** …`. Why: the queue's rule is one line per entry, and at the end `parseQueue`'s `body`, `isPending`, and `latestHalt` read the same as before. The format follows [decisions.md 2026-10-21](../decisions.md#2026-10-21--build-queue-answers-before-pod-reads-them); if claude-pod settles on another, the writer follows it.
- **Answerable** (`isAnswerable`). Pending, `needsYou`, type `PENDING` or `BLOCKED`, and no `answer`. A `NOTE` or `SOLVED` never is. An answer changes nothing else: the entry keeps `needsYou`, its run keeps `needs-you`, and an orchestrator `BLOCKED` keeps the plan halted, since pod still waits until it reads the line and resolves the entry. A line with no `**Resolution:**` isn't pending, so it's never answered (`parseQueue` would read an answer appended to it into the body).
- **Answer text** (`cleanAnswer`). Control characters that aren't whitespace (U+0000–U+001F, U+007F) drop first. Then every run of whitespace, line breaks and tabs included, becomes one space, and the text is trimmed. Empty → `Write an answer first.` Over 2000 characters (code points, after cleaning) → `Keep the answer under 2000 characters.` Holding `**Resolution:**` or `**Answer (` in any case → `The answer can't contain **Resolution:** or **Answer (…):**.` Why: one line, and no text that would change how the entry reads.

## Transcripts

`parseAgentTranscript({ id, session, meta, jsonl })` gets the text of `agent-<id>.meta.json` and `agent-<id>.jsonl`; the server finds and reads the files. It never throws.

- **Pod agents only.** `undefined` when `meta` isn't a JSON object or its `agentType` doesn't start with `pod:`. `type` is `agentType`. The meta file's `description` (the dispatcher's Task description, assistant-written text) is never read into the run, so it never reaches `/api/board`.
- **Dispatch.** `sprint`, `slice`, `branch`, `plan`, and `round` come from `readDispatch(prompt, agentType)` (`dispatch.ts`) of the first `user` record that has a prompt: its string content, or its first text block. Later user records (tool results, follow-ups) are never read for fields. `readDispatch` reads a field only where its name starts a line, a list item (`-`, `*`, `+`, `1.`, `1)`), a sentence (after `. `, name capitalized or bold), or a ` · ` part of a line that itself starts with any `Name:` (a word or words, then a colon; not only a field name), or where the whole field is one bold span anywhere (`— **round: 2**`). The name may be bold, with the colon inside or after the bold (`**slice code:** D1`, `**slice code**: D1`), and may carry a bracketed note (`**plan slug (= plan branch):** x`). Backtick spans never count, and a name mid-sentence never counts unless the whole field is one bold span. Names: `sprint slug`, `slice code`, `branch` or `branch name` (`merge-target branch` is not `branch`), `plan slug`, `plan`, `round` (a whole number above 0). The value is an optional backtick, then letters, digits, `_`, `.`, and `-`, so it ends at the first space (`Plan: Pod Board` → `Pod`); trailing dots drop (`alpha.` → `alpha`); a value followed by `/` or `\`, or by `:` and then `/` or `\` (a drive path: `E:/…`, `E:\…`, backticked or not), is a path and gives nothing (`- **plan:** pod-docs/plans/x.md` and `Plan: E:/r/pod-docs/plans/x.md` → no plan, not `E`; its base name isn't read, because a plan file's name isn't always the plan the agent works on). A `:` with no slash after it ends the value as usual (`alpha: the first plan` → `alpha`). Fenced code blocks (```` ``` ```` or `~~~`, fence lines included) never count, like backtick spans: a fence may open after an indent or a list marker, closes on a line of only the same character at least as long, and an unclosed fence runs to the end of the prompt, as in CommonMark; a ```` ``` ```` line whose info text holds a backtick is inline code, not a fence. The planner prose skips fenced blocks too. Per field name, the first place the name appears, in document order, wins, even when its value gives nothing: a later line with the same name is more likely a quote than the real field. Across the plan's sources, the first that gives a value wins, so one that gives nothing (no field, or a path) never blocks the next: a `plan slug` field; a `plan` field (the reviewer's dispatch); then, for a `pod:sprint-planner` or a `pod:reporter` only, the exact prose form ``for plan `<slug>` ``. The reporter needs it because `/pod:code`'s plan-complete dispatch can name the plan only in prose (``… feature details for plan `ui-polish` in …``, with `- Plan: pod-docs/plans/ui-polish.md`, a path that gives nothing). The 2026-10-20 check of 469 real `pod:*` transcripts changed only those 2 reporters (chess-web `ui-refresh` and `ui-polish`, from no plan to their own plan); the other 13 reporters already read the right plan from a `plan slug` field. So ``Plan: E:/…/plans/x.md. Draft the next sprint doc for plan `x`.`` reads plan `x`. The 2026-10-19 check of 448 real `pod:*` transcripts gave the same fields with either per-name rule (first match or first valid match), so the choice changes no real dispatch yet. Engineers, fix engineers included, never get a plan, even from a plan field: they join a plan by sprint, slice, or branch. Why: dispatch prompts quote findings and fix summaries, so field names show up in prose (``a `plan slug:` field``); the ported loose `parseDispatch` match took the first one anywhere, so a round 2 reviewer read plan `field`. But real dispatches write fields in many shapes: one per line with no marker, several on one line joined with `·`, bold with no marker, and planner prompts as sentences (`… repo. Plan slug: x.`). Reading only list items (plan board-read fix 2) lost the slice and branch of most running engineers. The pod-flow copy keeps its loose rule unchanged; the board doesn't call it.
- **Reviewer kind and PR.** For a `pod:reviewer` only, `kind` is the `kind` field (`plan` or `fix`) and `pr` the number of the first `PR URL` or `PR` field whose value is a GitHub pull URL (`https://github.com/<owner>/<repo>/pull/<N>`, optionally in backticks or `<>`), read at the same field starts as the other fields (not as a whole bold span). A `PR` field whose value isn't such a URL (`PR: #22`) gives nothing and ends the search, like any field. Other roles get neither. Why: a `/pod:fix` reviewer joins its fix run by `kind: fix` plus its branch or PR (see `runs-and-pipeline.md`); `field()` reads a URL as a path and gives nothing, so the PR needs its own value rule. The 2026-10-20 check of 475 real `pod:*` transcripts read the same `sprint`, `slice`, `branch`, `plan`, and `round` for every agent as before; 53 reviewers gained `kind` and/or `pr`, and every `pr` matched the number on the prompt's own PR line. 21 of them are `kind: fix` reviewers (26 `kind: plan`, 6 with a PR and no kind); 16 of the 21 read a branch or a PR, and the other 5, all ytb-feed (`kind: fix. Review PR <url>, branch …`), read `kind` only, since their PR and branch are prose. Older plan reviewers' `final PR:` fields give no `pr`, which nothing needs.
- **Times.** `startedAt` and `lastAt` are the first and last `timestamp` that parses, in file order, over every record type.
- **Tokens.** `turnTokens` (input + output + cache writes; cache reads are left out) summed once per `message.id`. One message streams over several records with the same id, and only its last record has the final output count, so the last record's usage counts. Usage on a record with no `message.id` is skipped; a usage field that isn't a number counts as 0.
- **Model.** The `message.model` of the last assistant record that has one.
- **Ended.** The agent's last hand-back (a `tool_use` block named `SubagentHandback`, or an assistant record whose `stop_reason` is `end_turn`) comes after its last prompt. A prompt is a `user` record whose content is a string or holds a text block and no `tool_result`. In real transcripts most agents end on the hand-back, whose record has `stop_reason: null`. Why: an agent continued with SendMessage gets a new prompt in the same transcript and works again; reading any hand-back as the end showed a round 2 reviewer as `ended` while it ran, so its fix run read `needs you` (PR #23 round 2).
- **Turns.** A prompt after a hand-back whose record has `origin.kind: "coordinator"` (a SendMessage resume) starts a new turn. Any other prompt after a hand-back (a `task-notification`, or a meta nudge) re-opens the turn it answers: the agent works again, but no new turn starts. Only an agent with two or more turns gets `turns` (each `{ startedAt, endedAt?, lastAt, tokens }`: from its prompt to its first hand-back after it, and the tokens of the messages that finished in it) and `resumedAt` (the last turn's start). Times and tokens only, never the prompt's text. Why: a fix run splits a continued engineer into build and fix pass, and a continued reviewer into round 1 and round 2, with each round's own times. The 2026-10-20 check of 490 real `pod:*` transcripts found 48 coordinator resumes, 17 task notifications, and 1 nudge after a hand-back. It gave 43 agents `turns` (38 with 2, 5 with 3) and changed no other field. `ended` changed for 2: pod-board `a31b714fcabe030d3` (this fix's engineer, working in its third turn, `true` → `false`, right) and ytb-feed `a1047952ef34f1d9a` (sent a task notice and then a user line on 10-16 and never answered, `true` → `false`, so it reads `stale`, which is right for an agent that stopped mid-turn).
- **Bad input.** A line that isn't JSON, a partial last line, a record that isn't an object, or one missing fields is skipped.
- **No text kept.** Only the fields above leave the parser; transcript text, tool input, and tool output never do.
- **State.** `agentState(a, now)`: `ended` → `'ended'`; else `now - lastAt < STALE_MS` (30 minutes) → `'running'`; else, or with no `lastAt`, `'stale'`. A `lastAt` ahead of `now` (clock skew) reads as running.

## Tool timeline

`parseAgentTimeline({ agentId, jsonl, roots })` in `packages/model/src/timeline.ts` turns one agent's transcript into an `AgentTimeline`: one event per tool call and the agent's test progress. The server passes `roots: [repo.path]`. It never throws.

- **No text leaves it.** A summary is built only from the tool name, file paths, and fixed words. Assistant text, thinking, prompts, tool output, command arguments, search patterns, edit contents, and URLs beyond the host never do. Why: transcripts can hold secrets, and the board serves the timeline to a browser.
- **Events.** One per `tool_use` block in `assistant` records, deduped by `tool_use.id`, because a block repeats over a message's streamed records (a block with no id counts each time). `at` is the record's timestamp; a block in a record with no valid timestamp is skipped. `result` comes from the first `tool_result` with that `tool_use_id` that comes after the call: `is_error: true` → `failed`, else `ok`; none yet → absent. Events sort oldest first (file order on a tie) and the newest 300 are kept; `total` counts all.
- **Tool name.** Kept when it matches `^[\w:.-]{1,64}$`, else `tool`.
- **Paths** (`file_path`, `notebook_path`, `path`): `\` → `/`; after `/.claude/worktrees/<name>/` → the rest; else after a root (any case, on a `/` boundary) → the rest; else the base name. Over 60 characters → `…` and the last 59.
- **Summaries.** Read, Edit, Write, MultiEdit, NotebookEdit → `<Tool> <path>`. Grep, Glob → `<Tool>`, plus ` in <path>`. Task, Agent → `<Tool>: <subagent_type>`; Skill → `Skill: <skill>` (when it matches `^[\w:.-]{1,40}$`, else the tool name). WebFetch → `WebFetch <hostname>` (only `^[a-z0-9.-]+$`). SubagentHandback → `Hand-back`. Anything else → its name.
- **Shell** (Bash, PowerShell): `<Tool>: ` plus up to 3 segments joined by ` · ` (then ` …`). The command splits on `&&`, `||`, `;`, `|`, and newlines; tokens holding `=` are skipped; the program is the first token's base name without `.exe`, shown only when it's a known program (else `command`). Only programs that take subcommands show one: the first of that program's own subcommands among the next four tokens. Those programs are the package managers (pnpm, npm, yarn, bun), deno, cargo, go, git, gh, agent-browser, vitest, vite, and corepack, each with its own fixed list in `SUBCOMMANDS`. So `pnpm --filter x test` → `pnpm test`, `git -C test status` → `git status`, and `echo test`, `grep -r test src`, `ls test`, `cat test.md` → just the program. Why: a word after `echo` or `grep` is an argument, not a subcommand.
- **Runners and scripts.** After a package manager's `exec` or `dlx`, and after `npx` or `bunx`, the first token that isn't a flag is the program it runs; its base name shows when it's a known program (`pnpm exec vitest`, `npx jest`, `npx tsc`), else nothing more (`npx cowsay test` → `npx`). After a package manager's `run`, the first token that isn't a flag shows when it's one of the fixed script names (`test`, `build`, `dev`, `verify`, `typecheck`, `lint`, `start`, `vitest`): `npm run test`. Quoted arguments, and any word not on these fixed lists, never show.
- **Tests.** A test run is a shell event with a segment that runs `vitest` or `jest` (as the program, or after `exec`, `dlx`, `npx`, or `bunx`), or whose subcommand is `test`, `verify`, or `vitest` on a package manager, deno, cargo, or go, or whose script after `run` is one of those. Why: counting the test runner after `exec` or `npx` is the safest reading of test progress; git, gh, and every other program never run tests. `runs`, `failedRuns`, and `last` count finished runs only (those with a result). `testFiles` counts distinct edited paths (Write, Edit, MultiEdit) matching `.test.` or `.spec.` before a JS or TS extension, or under `__tests__/`. `testFirst` is absent with no test-file edit; else `true` unless a code file (not a test file, not `.md`, `.json`, `.yaml`, `.yml`, `.lock`) was edited first.

## Watch out

- Of the fixtures, only chess-web's `ladder.md` keeps its `### ` slice sections. Other fixture sprint docs read with no `model` and `filesOwned: []`.

- The ported `parseSprint` reads `Slug:` with `[\w-]+`, which takes `_`. A header that ends right after the slug (`· Slug: ladder_`) reads as `ladder_`. Real docs always have `· Status:` after it, so it hasn't bitten yet.
- `parsePlan` defaults a missing plan status to `active` and a missing sprint-row status to `planned`.
- A program not in `SUBCOMMANDS` never shows a subcommand and never counts as a test run. Add a program there (with its own list) before expecting its runs to count; a new word on any list must be safe to show.
- Scripts with other names don't count as test runs: `pnpm run test:unit` reads as `pnpm run`, and `npm run my-tests` too. A runner given a flag with a separate value (`npx -p pkg vitest`) reads `pkg` as the program, so it isn't counted. `node node_modules/vitest/vitest.mjs` reads as `node`.
- A field counts only at a line, list item, sentence, or ` · ` part start, or as a whole bold span. A pod prompt that names a field another way (a table, `slice code D1` with no colon, `the plan: alpha` mid-sentence) gives that field nothing. A ` · ` part counts only when its line starts with a `Name:`, so a pasted queue entry (`[date · TYPE · … · plan: x]`) reads nothing, but `- Queue: [… · plan: x]` reads `x`. A sentence in unquoted prose that starts with a capitalized field name (`… done. Round: 3 …`) would count; the 2026-10-19 check of 445 real `pod:*` transcripts found no wrong value from it.
- Round 4 listed loose edges that read wrong only on made-up prompts: `e.g. Round: 7` (a sentence start after an abbreviation), a lowercase `. **plan:** x`, a `·` part after any `Name:`, a value cut at a space, and a whole bold span mid-sentence. They're queued as someday; round 5's re-scan of 456 real `pod:*` prompts (2026-10-20) found no wrong value. Run the same before-and-after corpus check for any change to these rules ([decision](../decisions.md#2026-10-19--fix-the-dispatch-field-regression-with-a-corpus-check)).
- The planner's and reporter's plan can come from prose, so it holds only while pod's prompt says ``for plan `<slug>` ``. An engineer's or reviewer's prompt can quote that phrase (pasted findings, context), so the prose rule stays with planners and reporters. A new agent type that names its plan only in prose needs a dispatch field or its own rule here.
- An untagged queue entry joins a plan only by its leading `plan <slug> complete`. A hand-back worded another way (`Final PR for ui-polish …`) with no `plan:` tag stays on the repo, and the claimed run reads `closing out` until the claim goes.
- An unclosed fence blanks every line after it, so a stray ```` ``` ```` line in a prompt loses every later field. A fence opened on a list item (```` - ``` ````) closes only on a line of the fence alone. Real prompts had no line-start fence as of 2026-10-19.
- 5 real `pod:sprint-planner` prompts (2026-10-19 check) name their plan only as a drive path, mid-sentence, with no ``for plan `<slug>` `` prose, so they read no plan and their sprint shows `not drafted` while they run. A planner prompt needs a plan field or that prose for the board to place it.
- Tests under `packages/model/src/` must build `RepoFiles` and transcripts inline (the no-I/O test scans that folder). Tests that read fixtures go in `packages/model/test/fixtures.test.ts`.
